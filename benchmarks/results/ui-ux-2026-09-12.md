# UI/UX Validation — 2026-09-12

## Result

The new skill is loadable, the analyst can use Mobbin and the permitted browser commands, and the structural checks pass. The offline comparison produced useful, task-specific decisions on both sides. It does **not** establish a large quality improvement or better outcomes for real users.

Suite: [UI/UX decision quality](../ui-ux.md). Fixture: [four fixed cases](../fixtures/ui-ux-cases.json).

## Offline comparison

- Baseline: the previous `web-designer` router/leaves and the analyst prompt from Git HEAD.
- Candidate: the new `ui-ux` router/leaves and the updated analyst prompt.
- Model and reasoning variant: `openai/gpt-6-astra`, `xhigh`, on both sides.
- One request per side, with all four cases in the same context. Relevant guidance was supplied explicitly; tool use was disabled. The rubric was not included in the model input.
- Both requests completed normally and answered all four cases. This was a self-reviewed, single paired run, not independent repeated trials or a blinded evaluation.

| Case                            | Observed result                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| UXQ-01 — Shipment queue         | Both retained comparison, made Dispatch selection-scoped, and distinguished the 16 px glyph from its 32 px button. The candidate explicitly specified filtered-out selections, a horizontally scrolling compact table, and the added selection step for single dispatch. The baseline also provided strong cross-page selection and recovery guidance. |
| UXQ-02 — Accepted visual update | Both gave a scoped visual pass with no invented findings. Both preserved the accepted gradient and equal peer cards, and distinguished missing interaction evidence from an observed defect. No meaningful advantage established.                                                                                                                      |
| UXQ-03 — Wholesale checkout     | Both reduced repeated entry, rejected billing-equals-delivery as the default for the supplied buyer population, differentiated invalid email from an uncertain timeout, and withheld functional acceptance. The baseline targeted Delivery → Billing → Review; the candidate avoided committing to three stages before establishing task coherence.    |
| UXQ-04 — Ceramics opening       | Both proposed concrete photography-led openings with comparison facts, a truthful collection link, compact behavior, and a rendered checkpoint. The candidate kept named existing type roles and made the compact comparison tradeoff explicit. Neither rendered or user-tested the proposal.                                                          |

Input tokens were 11,473 for the baseline and 18,092 for the candidate: approximately 58% more in this fully preloaded, four-case comparison. That is a context-cost tradeoff, not a measurement of normal on-demand skill loading.

All candidate guidance hashes still match the tested files. The agent file changed after the offline run; its recorded hash identifies the tested snapshot. The subsequent live capability check used the final configured analyst. The old router has since become a compatibility alias, so rerunning the baseline requires its preserved input rather than loading today's alias.

## Limits

These checks establish configuration operability and a small sample of bounded design reasoning. They do not prove rendered design quality, native mobile behavior, accessibility conformance, task-completion gains, conversion gains, or reliable superiority across projects. The worked cases are evidence-backed examples of decision-making, not universal prescriptions. Applying the skill to real product work still requires inspecting the rendered result and validating the material task assumptions.
